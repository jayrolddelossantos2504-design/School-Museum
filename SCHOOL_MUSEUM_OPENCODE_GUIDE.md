# School Museum Website — Project Guide for OpenCode

## 1. Project purpose

Build a public-facing School Museum website where visitors can browse museum items online and scan a unique QR code attached to each physical item to open its public detail page.

Authorized school staff manage the collection. The commissioner provides the initial set of images and descriptions; staff can add more items and update the collection later.

## 2. Required technology stack

- **Backend:** Python with Flask
- **Database:** MySQL (or MariaDB through XAMPP during local development)
- **Database driver:** `mysql-connector-python`
- **Templates:** HTML using Flask/Jinja templates
- **Styling:** CSS, with JavaScript where useful
- **Authentication:** `Flask-Login`
- **Form and CSRF protection:** `Flask-WTF`
- **Environment variables:** `python-dotenv`
- **Image storage:** Cloudinary; store image URLs and Cloudinary public IDs in MySQL, not the image bytes
- **QR codes:** `qrcode[pil]`
- **Production server:** A suitable WSGI server such as Waitress, or the host's recommended server

Keep the architecture simple and suitable for a student project. Do not introduce a new framework, database, or major dependency without explaining why and asking first.

## 3. Core user roles

### Public visitor
- Browse published museum items without creating an account.
- Search items and filter by category.
- Open an item's detail page from the collection or by scanning its QR code.
- View item images, descriptions, historical details, and category.

### Administrator
- Log in securely.
- Manage staff accounts and roles.
- Add, edit, publish, unpublish, and archive museum items.
- Manage categories.
- Upload and replace images.
- Generate, download, and print item QR codes.
- Review who created or edited items if activity logging is implemented.

### Editor / authorized staff
- Log in securely.
- Add and edit museum items and upload images.
- Do not manage administrator accounts unless explicitly granted permission.

Enforce permissions on the server for every protected route. Hiding a button in the interface is not access control.

## 4. Main functional requirements

1. Public home page introducing the school museum.
2. Collection page with item cards, search, category filters, and pagination when needed.
3. Individual public detail page for each published item.
4. Secure staff login and logout.
5. Admin dashboard and item management.
6. Item form with name, description, historical details, category, image upload, and publication status.
7. Support one or more images per item, with a designated cover image.
8. Each item receives a permanent, unique public identifier (UUID).
9. Generate QR codes from the permanent public URL, not from an image URL or database row number.
10. Editing an item or replacing its image must not change its public URL or QR code.
11. Draft/unpublished items must not be visible to public visitors, even if someone knows their URL.
12. Validate uploads and protect all write actions against CSRF.
13. Responsive design suitable for mobile phones, since visitors will scan QR codes on their phones.
14. Public deployment must use HTTPS and a stable domain before QR codes are printed for long-term use.

## 6. Database design

Use a database named `school_museum` with UTF-8 (`utf8mb4`) encoding.

Suggested tables:

### `admins`
- `AdminID`: primary key
- `Username`: unique username
- `Password_Hash`: password hash generated with a secure password-hashing library or Werkzeug
- `Role`: `admin` or `editor`
- `Created_At`: timestamp

Never store plain-text passwords.

### `categories`
- `CategoryID`: primary key
- `Category_Name`: unique category name
- `Description`: optional category description

Example categories: Historical Artifacts, Photographs, Documents, Memorabilia.

### `museum_items`
- `ItemID`: primary key
- `Public_Token`: unique UUID string, generated by the application
- `Item_Name`: required item name
- `Description`: required public description
- `Historical_Details`: optional historical background
- `CategoryID`: nullable foreign key to `categories`
- `CreatedBy`: nullable foreign key to `admins`
- `IsPublished`: boolean, default false
- `Date_Added`: creation timestamp
- `Updated_At`: update timestamp

### `museum_item_images`
- `ImageID`: primary key
- `ItemID`: foreign key to `museum_items`
- `Image_URL`: secure Cloudinary URL
- `Image_Public_ID`: Cloudinary public ID used to manage the image
- `Is_Cover`: boolean indicating the main image
- `Uploaded_At`: timestamp

Use foreign keys and suitable indexes. When an item is deleted, its related image records should be handled consistently. If an item is archived, consider keeping the record and disabling public access instead of permanently deleting it.

MySQL stores item metadata and image references only. Store image files in Cloudinary (or another configured object-storage service), not as large BLOBs in MySQL.

## 7. Image upload workflow

The commissioner supplies the initial images and associated information. An authorized staff member imports/uploads those materials using the same admin interface that will be used for future items.

For each image:
1. Require an authenticated, authorized user.
2. Check that a file was provided and enforce a configured size limit.
3. Validate the file content and allowed image formats; do not trust the filename or browser-provided MIME type alone.
4. Use safe generated filenames or the Cloudinary SDK; do not use an untrusted filename as a filesystem path.
5. Upload the image securely to Cloudinary from the server.
6. Save the returned secure URL and public ID in `museum_item_images`.
7. Allow the user to designate a cover image.
8. When replacing/deleting an image, update the database and remove the old Cloudinary asset when appropriate.
9. Handle upload/database failures so records do not silently point to missing images.

Keep the Cloudinary API secret on the server and in environment variables. Never expose it in templates, browser JavaScript, or source control.

## 8. QR code behavior

Create a permanent public URL for each item using its UUID token, for example:

`https://museum.example.org/item/<public-token>`

The domain above is illustrative and must be replaced with the real deployed domain.

Generate QR codes using Python's `qrcode` package. The QR code must encode the permanent item URL, not the image URL. Provide a download/print action for authorized staff.

The public detail route must:
- Find the item by `Public_Token`.
- Return a 404 for unknown tokens.
- Show only published items to anonymous visitors.
- Preserve the same URL when item text or images change.

Do not print permanent QR labels using `localhost`, `127.0.0.1`, or a temporary hosting URL. Configure the final HTTPS `SITE_URL` before generating labels for physical displays.

## 9. Environment variables

Use `.env` locally and the hosting platform's secret/environment-variable settings in production.

Example `.env.example` (placeholders only):

```dotenv
SECRET_KEY=replace-with-a-long-random-secret
DB_HOST=localhost
DB_PORT=3306
DB_USER=museum_app
DB_PASSWORD=replace-me
DB_NAME=school_museum

CLOUDINARY_CLOUD_NAME=replace-me
CLOUDINARY_API_KEY=replace-me
CLOUDINARY_API_SECRET=replace-me

SITE_URL=http://127.0.0.1:5000
MAX_CONTENT_LENGTH=10485760
```

- Never commit `.env`.
- Keep `.env.example` free of real credentials.
- Use a strong random `SECRET_KEY`.
- Create a dedicated MySQL application account with only the permissions required by the app; do not use the database root account in production.
- In production, use a real HTTPS domain in `SITE_URL`.
- `MAX_CONTENT_LENGTH` is an example 10 MiB request limit; adjust it to the project's needs and also enforce an upload limit in application logic.

## 10. Local setup

1. Install Python and MySQL, or start MySQL/MariaDB through XAMPP.
2. Create and activate a virtual environment:

   Windows:
   ```powershell
   python -m venv venv
   .\venv\Scripts\Activate.ps1
   ```

   Command Prompt:
   ```bat
   venv\Scripts\activate
   ```

3. Install dependencies from `requirements.txt`:
   ```bash
   pip install -r requirements.txt
   ```

4. Create the database by running `schema.sql` in MySQL Workbench or phpMyAdmin.
5. Create a dedicated database user and grant it access to `school_museum`.
6. Copy `.env.example` to `.env` and fill in local settings.
7. Run the Flask app using the project's documented development command.
8. Test the database connection before implementing the rest of the features.

Do not assume that the database user, password, or Cloudinary credentials are known. Ask the project owner to configure them locally.

## 11. Security requirements

- Hash passwords; never store or log plain-text passwords.
- Protect all admin routes with authentication and role checks.
- Use CSRF protection for forms that change data.
- Use parameterized SQL queries for all user-supplied values.
- Validate and limit image uploads.
- Keep secrets out of source control and browser code.
- Use secure session settings and HTTPS in production.
- Do not expose draft or unpublished items publicly.
- Avoid displaying internal errors or credentials to users.
- Use safe output escaping in Jinja templates.
- Confirm permissions for edit, delete, upload, publish, and QR-download routes.
- Use a stable public HTTPS URL for printed QR codes.

## 12. Development milestones

Implement one milestone at a time and test it before moving on.

### Milestone 1 — Foundation
- Project structure and dependency file
- Environment-variable configuration
- MySQL schema and connection
- Health-check route

### Milestone 2 — Authentication
- Secure login and logout
- Initial administrator creation via a safe setup script or CLI command
- Role-based access control
- Protected admin dashboard

Do not insert a default administrator password into source code or publish an admin account with a known password.

### Milestone 3 — Item management
- List, create, edit, publish/unpublish, and archive items
- Category selection and management
- Audit fields for creator and timestamps

### Milestone 4 — Image management
- Cloudinary integration
- Upload validation and size limits
- Multiple images and cover-image selection
- Replace/remove images safely

### Milestone 5 — Public website
- Home page and collection page
- Search, category filters, pagination
- Responsive item detail pages
- Public visibility restrictions

### Milestone 6 — QR codes
- Permanent UUID-based URLs
- QR generation, download, and print-friendly layout
- Test QR codes with a phone using mobile data

### Milestone 7 — Deployment
- Production database and image storage
- HTTPS and stable domain
- Production WSGI server
- Backups, error logging, and deployment testing

## 13. OpenCode working instructions

When working in this repository:

1. First inspect the existing files and explain the current structure before making large changes.
2. Follow the stack and requirements in this guide.
3. Work in small, testable steps; do not generate the entire system in one unreviewed change.
4. Before editing, identify which files will change and briefly explain why.
5. Do not overwrite existing work without checking it first.
6. If something is ambiguous, ask a focused question rather than inventing project requirements.
7. After changes, explain how to run and test them and report any tests that were not run.
8. Do not claim a feature works unless it has been implemented and tested.
9. Keep secrets and real credentials out of code, logs, documentation, and commits.
10. Prefer readable beginner-friendly code and comments where they clarify non-obvious behavior.
11. Use parameterized database queries, server-side authorization, and upload validation by default.
12. Do not switch technologies or add large dependencies without explaining the tradeoff and asking first.

## 14. Definition of done

The initial version is ready for review when:
- Staff can securely log in.
- Authorized staff can add an item with a valid image and description.
- The item record is stored in MySQL and its image is stored in Cloudinary.
- Staff can edit an item without changing its public token.
- Visitors can browse published items without logging in.
- Unpublished items remain private.
- Every published item has a scannable QR code that opens its correct page on a phone.
- The deployed site works over HTTPS with a stable domain.
- The setup and testing steps are documented.

## 15. Important implementation note

This document is the project specification, not proof that the application has already been implemented. Inspect the repository and build each milestone incrementally. Keep the database schema, Flask code, templates, and this guide in sync as decisions evolve.
